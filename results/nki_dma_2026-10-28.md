# NKI kernel: fewer DMAs per multiply (trn1, 2026-10-28)

Two changes to the sliced-ELL kernel (nki_sell.py), measured one after the other:

- **v1** (main): per slice, two small DMAs copy its index tables, then gathers, then one indirect-DMA scatter
  per pass to put the 128 results in their rows.
- **v2**, tables up front: runs of slices share one table copy (TABLE_COLS = 4096 columns per partition, so
  one copy per table for every matrix below).
- **v3**, block writes: in "ordered" mode (`make_sell_kernel(ordered=True)`, `MatVec(permute=True)`, used by
  the batched solver), Y comes out in the layout's own row order. A slice of whole rows then writes its
  results as one contiguous block, a plain DMA, instead of scattering. Only slices holding pieces of split
  rows still scatter. `batch._stream` permutes its inputs into that order and the solutions back out.

Scatters per multiply, v2 → v3:

| matrix | K | K^T |
|---|---|---|
| chromaticindex512-7 | 264 → 0 | 544 → 256 |
| neos-4300652-rahue | 610 → 11 | 264 → 8 |
| neos-933966 | 98 → 10 | 249 → 0 |

The 256 left in chromaticindex512-7's K^T come from 3 slices holding most pieces of one 6,144-entry column.
A scatter-add needs distinct target rows, so each piece takes its own pass.

| | v1 | v2 | v3 | v1 → v3 |

| K: kernel time (ms) | 4.76 | 4.53 | 4.07 | -15% |
| K: DMA transfers | 1,849 | 1,323 | 1,322 | |

| K^T: DMA transfers | 2,184 | 1,604 | 1,604 | |

What each DMA costs on trn1, from the differences: a plain table copy ~0.4 us, and a scatter replaced by a
block write saves ~1.7 us. Gathers make up the rest. Their descriptors are generated in software one at a
time, and the chip is idle ~80% of the kernel's run.

where fixed per-DMA costs weigh most, and on neos-4300652-rahue, which had the most scatters (all of them

First-solve (compile) times aren't compared here. In the afternoon the box was shared with another session's
compiles, and back-to-back reruns of the same version varied by 20 s. Compiling the kernel on its own takes
about the same time in every version (2.7-2.9 s for chromaticindex512-7).

## Correctness

- Simulator: the ordered kernel's output is K @ X in `output_order`, for matrices with and without split rows
  and with several table groups (`tests/test_nki_sell.py`). Permuted MatVec and a batched solve through it
  also match.
- trn1: the same through `nki` and `nki-op`, plus a batched solve of shell.mps (split rows) whose solutions come
  back in the LP's own order: the objective equals c @ x, and x is feasible to the reference's accuracy. The
  full suite passes on the chip: 175 passed, 5 skipped.
- Solutions can differ slightly from the unpermuted path's. Norms and sums now add their entries in another
  order, so float32 runs can end at a different optimum within tolerance. In one simulated 4-LP batch at
  tol 1e-4, one LP's objective differed by 1.3e-4 relative.

## What's left

- The gathers: about one per 128 nonzeros, already at the floor for one-row-per-lane gathers. Cutting them
  needs a multi-row gather (2D `vector_offset`, which doesn't compile for trn1) or hardware descriptor
  generation (trn2?).
- Split-row slices with many passes (chromaticindex512-7 K^T: 3 slices, 256 scatters). Summing a row's pieces
  within the slice first, for example with a 0/1 matmul on the Tensor engine, would make that one pass per
  slice.
- The single-LP solver (`pdlp.py`) still uses the unordered kernel. It could adopt `permute=True` the same
  way `batch.py` did.
